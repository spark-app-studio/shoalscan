# Changelog

All notable changes to Shoalscan are recorded here.

## Unreleased

### Added

- `shoalscan scan --changed-only`, with `--policy-ref`, scans only the files a pull request changed, and `check` with the same `--policy-ref` judges only those files. The verdict on a changed file is a full scan's: the walk keeps the same excludes, size limit and symbolic-link handling, and anchored `--include` patterns narrow it, because Opengrep scans an explicit target even where an exclude or the size limit would have left it out. The list of changed files comes from git (renames split into a deletion and an addition, untracked files included), is recorded in `findings.json` under `changed`, and is listed again by `check`, which refuses findings whose list differs. Baseline entries of unchanged files are carried over without being judged (`baseline_not_judged`), and only changed or deleted files can leave stale entries. The scan stops when Opengrep scans a file outside the changed files, leaves a changed file out, or scans a file Shoalscan reads as excluded, and it refuses a base that is not an ancestor of `HEAD`, more than 2000 changed files, file names an `--include` pattern would read as a glob, and configurations with scanners other than Opengrep. Changed files no loaded rule reads are named (`changed_unread`); a changed file that a loaded rule's language reads (by extension, Dockerfile name or shebang, from Opengrep 1.30.2's language table) but Opengrep did not list stops the scan. A `generic`, `aliengrep` or `regex` rule reads the files its `paths: include` globs match, and every file when it has no include. History schema version 17 records each run's scope (`full` or `changed`); a scan of changed files is recorded only as a pull-request run, and the dashboard marks it. See [Scanning only the changed files](docs/baseline-and-check.md#scanning-only-the-changed-files).

## 0.4.0 (2026-10-24)

### Added

- `shoalscan scanjob --pull-requests` scans the open pull requests of a public repository itself, with no credentials, so a public repository's pull requests never need to run on your own CI runners. Set `pull_requests = true` by hand on a target with an https `source` in `scan_targets.toml`. Everything in a pull request is treated as written by an attacker. See [Scheduled scans](docs/scheduled-scans.md#scanning-the-open-pull-requests-of-a-public-repository), with the limits of finding open pull requests this way.
  - Discovery is one anonymous, hardened `git ls-remote` with `HOME=/nonexistent` (never the GitHub API). A pull request is a candidate when it has a `refs/pull/N/merge` ref, an earlier run of its `refs/pull/N/head`, or, by a per-target poll state, a number above the first poll's high-water mark or a head that moved since the previous poll (so one that conflicts from its first push is still scanned, and closed ones are not).
  - Each head is fetched anonymously into a throwaway repository that borrows the branch clone's objects read-only, so the branch clone never grows or breaks, size-checked before checkout, scanned like a scheduled scan and recorded as a pull-request run of `refs/pull/N/head`. A pull request pushed to after the listing is scanned at the head that was fetched.
  - The policy and baseline are the target's, the repository rule directories come from the head of the registered branch, and changed files are listed against the merge base with it. Inline suppressions the pull request adds on its changed lines fail it, and so does new code an existing marker silences; stale baseline entries are only reported. A head is scanned again when the registered branch's head or the target's policy or baseline file changes.
  - Fairness and budgets: pull-request scans have their own `max_pr_scans_per_hour` (default 6), apart from the dashboard's `max_scans_per_hour`; at most `max_pull_requests` (default 10) per poll; a pull request at most once an hour, counted from its last attempt; never-scanned and longest-waiting first, so new pull requests can push rescans of older heads to later polls. A failure the pull request caused is recorded as a scan error and retried only after a day, while it looks open, or when the head changes; a failure of this machine is retried on the next poll, and an attempt that ran no scan gives its budget back. Closed pull requests are never retried or rescanned.
  - A listing that fails, times out, is malformed or does not show the registered branch, or an unreadable poll state, is recorded as a scan error, never as nothing to scan. Nothing is posted to GitHub.
  - Example launchd and systemd units run it every 15 minutes.
- The Runs page shows a **Pull requests** table with each pull request's latest run: its number, head commit, status and the reason for a failed scan, new blocking and new findings, changed files that were not fully scanned, suppressions and new suppressions, and its number of runs. `/api/runs` returns it as `pull_requests`.
- `shoalscan scan --rules-commit <commit>` reads the repository rule directories from that commit instead of the scanned tree (with `--config`), and records it in `findings.json` under `policy.rules_commit`. `shoalscan check --changed-since <commit>` lists the changed files against the merge base with that commit, with an explicit configuration and baseline: a changed file that was not fully scanned and an inline suppression on an added line fail, and stale baseline entries are only reported. The added lines come from a textual diff (`--text`), a changed file with no textual diff counts in full, and Trivy markers in a changed chart archive count as new. `findings.json` lists every finding a scanner silenced because of an inline comment (`silenced_list`, `silenced_total`), and `check --changed-since` fails those whose lines overlap the added lines, even under a marker that was already there. When the scan listed only part of them (over 10,000), the check stops with a setup error rather than guess. History schema version 16 stores the new suppressions.
- Every scan, scheduled scans included, checks the commit's tree before checking it out: past `max_checkout_mb` (default 2048), `max_checkout_files` (default 200000), a path deeper than 64 directories, or not enough free space for the checkout twice (in whole 4 KiB blocks, plus 4 KiB per file) besides `min_free_mb`, the scan is refused. The size is also watched while git writes the checkout. A scheduled scan of a repository past these limits now fails until they are raised.
- `shoalscan record --max-pr-runs` (default 2000) caps the pull-request runs kept per repository, counted apart from the scheduled runs `--max-runs` keeps.

### Changed

- `check --changed-since` no longer fails on stale baseline entries: the change cannot edit the outside baseline, so they are reported only. `check --policy-ref` and plain checks still fail on them.
- The text embeddings are made from, the similar-finding description, the line a "fixed" review is verified against and the line `triage export` writes come from scheduled runs only.
- The Overview's latest run, the repository list, the Configuration page's last run, the scanners in use and the trends use scheduled runs only. A repository without scheduled runs no longer falls back to its pull-request runs.
- Pull-request runs never push scheduled runs out of the history: the two kinds are pruned apart.

### Fixed

- Hardening: network git commands of the scan worker run without the home directory, so curl never reads a `~/.netrc`, and scanner output loses control, escape and bidirectional characters before it is written to the scan log.
- The dashboard and the scan worker change `scan_requests.json` under a shared lock.
- Hardening: every git command Shoalscan's checks run treats file names as literal paths (`GIT_LITERAL_PATHSPECS`), so a file a change names like pathspec magic (`:(exclude)*.py`, `:(glob)**`, `:/x`) can no longer hide its added lines from `check`; a changed file whose diff is empty counts as added in full. The worker's own git commands use literal pathspecs too.
- Hardening: the diffs `check` reads ignore the repository's `.gitattributes` and the machine's system and global git configuration (`GIT_ATTR_SOURCE` set to the empty tree, no system or global configuration, `--no-ext-diff`, `--no-textconv`), so no clean filter can reshape them. `scan --policy-ref`, `check --policy-ref` and `check --changed-since` need git 2.40 or later and refuse an older git, which would silently ignore the attribute source and let the change's `.gitattributes` apply: **CI on Ubuntu 22.04 (git 2.34) needs a newer git**, for example from the git-core PPA. Each git command passes `-c safe.directory` for exactly the repository path it was given, since global configuration is no longer read.
- git's output is read as it is written and capped at 256 MB, instead of being buffered whole first.
- Hardening: `check` (in a git work tree) and the scan worker refuse a path that is not valid UTF-8 or holds a control character, with exit 2 or a scan error. The scanners report such a name differently (Opengrep as U+FFFD) or not at all, so its code could pass unscanned and its suppressions unseen. **A repository with such a file name now fails its checks until the file is renamed.**

## 0.3.1 (2026-10-17)

### Fixed

- `[limits] jobs` now also bounds Opengrep's rule loading, not only its matching. Opengrep loads rules with a thread pool sized from the machine's core count (`min(32, cores + 4)` workers, each starting an `opengrep-core` process), whatever `--jobs` says, so a scan briefly used most of the machine's cores. Shoalscan now sets `PYTHON_CPU_COUNT` to `jobs` in Opengrep's environment, which gives that pool `min(32, jobs + 4)` workers, and records `jobs` and `python_cpu_count` under `scanners.opengrep` in `findings.json` ([Configuration](docs/configuration.md#jobs)).

## 0.3.0 (2026-10-13)

### Added

- Test code labels: a Rust finding whose code lies inside a top-level `#[cfg(test)]` or `#[cfg(all(test, ...))]` module, function, `impl`, constant or static gets a **test code** label, for the Opengrep rules listed under the new `[test_code] rules` (off by default; read from the base branch under `--policy-ref`). Labels are triage help, not a security proof: procedural macros, build tools, build scripts and build configuration can compile test code into a release, and a scanner cannot rule that out. Labelled findings are grouped apart in the scan output, `findings.json` and SARIF (`test_code`: kind, path and line), the check report (with `test_code`, `new_test_code` and `new_blocking_test_code` counts) and the dashboard (a tile, a filter and the label on each finding), and they block exactly like any other finding: nothing is resolved, reviewed or baselined automatically. Opengrep's own Rust parser finds the items, with a rule pack shipped and pinned with Shoalscan that runs in the same scan; a finding is labelled only when its whole byte range lies inside the item and the attribute is spelled exactly as recognised. Test functions, whole files (such as a crate's `tests/`), `cfg(any(test, ...))`, `cfg(not(test))`, `cfg_attr`, features, `cfg(r#test)`, nested items, `examples/`, `build.rs`, `src/bin/` and files Opengrep reported an error for get no label. A note says when the labels may be unreliable (a build script, a procedural macro crate, a linker or wrapper setting, or a Cargo or toolchain file Shoalscan does not fully understand); it never changes whether a finding blocks. Rules that find secrets, Gitleaks rules, other scanners' rules and broad wildcards such as `community.*` cannot be labelled. See [Test code labels](docs/test-code.md).
- A person accepts a labelled finding with the existing mechanisms: `shoalscan baseline accept --test-code --fingerprint <fp> --by <name> --issue <issue>` (or `--all`) adds baseline entries with the reason "Accepted: test code (...); accepted by <name> on <date>", under the usual baseline rules, and the dashboard's **Accept as test code** button records an accepted-risk review by the signed-in person, with a reason the server writes after checking the label. `triage export` exports only reviews a signed-in person made, and no longer repeats "Accepted:" in a reason. History schema version 14 stores each finding's label.

### Fixed

- `shoalscan serve` migrates an older history database at start, as `record` does, instead of refusing to start (a 0.2.0 dashboard would not open a 0.1.x database). Every migration first writes a copy of the database as it was, `history.sqlite3.bak-schema<N>` (mode 0600), and says so, so an older Shoalscan can be restored with it ([The dashboard](docs/dashboard.md)).
- Schema version 15 repairs a history database written by an unreleased 0.3.0 development build (other version-14 columns, and automatic "shoalscan (test scope)" reviews, which it removes and reports).
- Hardening: the dashboard compares the sign-in nonce, the login state and the CSRF token as UTF-8 bytes, so a value with characters outside ASCII is refused instead of ending the request with an error. Found by the `id_token_claims` fuzz target.

## 0.2.0 (2026-10-12)

### Added

- `shoalscan triage` prints a prioritised work list of the last scan's findings, offline, from `findings.json` and the baseline: stale baseline entries first, then one group per rule family (the CWE a rule names, or the rule itself), each with its rules' messages, fix hints, CWE and OWASP labels, references and a link to the rule file, and its findings by component, marked new and blocking, new, or baselined with their issue and reason. Groups follow the dashboard's Fix priority. `--format json` lists every finding for scripts and agents; `--blocking-only`, `--output` and `--max-per-group` shape the list. It warns when the tree, HEAD or configuration changed after the scan. `triage export` is unchanged.
- `shoalscan report` writes a dated security report on one repository from the run history, for a period of up to 366 whole UTC days (`--since`, `--until`; the last 30 days by default): the posture at the end of the period and its change since the start, blocking and untriaged findings, the weekly new and fixed findings with the lists behind them, the time to fix, what the baseline accepts grouped by issue and reason, dashboard review changes with who made them, components, coverage (runs by outcome, deleted runs, unscanned files, suppressions, scanner versions and signature checks) and the limits of static analysis. Markdown by default, or `--format json`.
- `shoalscan scan` records each reporting rule's metadata (CWE, OWASP, confidence, likelihood, impact, fix hint, references and rule file) under `rules` in `findings.json`. Values are bounded and only http(s) links are kept.
- Gitleaks 8.30.1 as a second scanner, for secrets: add `"gitleaks"` to `scanners`. `shoalscan install` pins and verifies its release archive, the binary in it and its default rules by SHA-256 (the project publishes no signature), and `scan` checks the binary and rules again before every run. Findings are ERRORs named `gitleaks.<rule>` under CWE-798, and appear in `findings.json`, the SARIF file (a run of their own), the check, the triage work list and the dashboard like any other. The About page lists Gitleaks.
- Hadolint 2.15.1 as a third scanner, for Dockerfiles: add `"hadolint"` to `scanners`. Shoalscan finds the Dockerfiles itself (outside `.git` and the excludes, no links, not over the size limit) and pins the binary by SHA-256. Findings are named `hadolint.<code>`; `error` becomes ERROR, `warning` WARNING, `info` and `style` INFO. A Dockerfile that does not parse is listed as not fully scanned. `[hadolint] ignore` in `.shoalscan.toml` leaves rules out, as policy. The About page lists Hadolint.
- zizmor 1.30.1 as a fourth scanner, for GitHub Actions: add `"zizmor"` to `scanners`. It audits the workflows in `.github/workflows`, every `action.yml` and `.github/dependabot.yml`, offline, with its regular persona. `High` becomes ERROR, `Medium` WARNING, `Low` and `Informational` INFO. A file zizmor cannot read is listed as not fully scanned while the others still count. `[zizmor] ignore` leaves audits out, as policy. Its release archives were verified against their build provenance when pinned, and are checked by SHA-256 at install and before every scan. The About page lists zizmor.
- Trivy 0.74.0 as a fifth scanner, for infrastructure as code (Terraform, CloudFormation, Kubernetes, Helm charts, Dockerfiles, Azure ARM, Ansible): add `"trivy"` to `scanners`. It runs offline with the checks embedded in the pinned binary. `CRITICAL` and `HIGH` become ERROR, `MEDIUM` WARNING, `LOW` and `UNKNOWN` INFO. Terraform files it cannot parse are listed as not fully scanned. `[trivy] ignore` leaves checks out, as policy. The About page lists Trivy.
- `tools.lock` can pin a signature for a scanner in its own table; `shoalscan install` then checks the download's Sigstore bundle with cosign before extracting it, as it does for Opengrep.
- Similar findings, with a local embedding model: `shoalscan triage embed` (or `shoalscan record --embed`) embeds a repository's findings with Ollama on this machine (EmbeddingGemma by default) and stores the vectors in the history database (schema version 12); `shoalscan triage suggest-similar <fingerprint>` lists the findings most like one, by cosine similarity, with the review or baseline decision made about each, and the dashboard's review page shows the same list. Only finding text (never code) is embedded, only through Ollama on the loopback interface, without proxies; when Ollama is unavailable, `record` warns and carries on. No new dependencies.
- Suggestions for untriaged findings: after embedding, each untriaged finding of the latest run gets the decision (false positive, accepted risk or won't fix) of its most similar decided finding, above `--threshold`. The Findings page shows it in a new **Suggestion** column with a link to that finding, filters for **Untriaged, with a suggestion**, and **Use the suggestion** fills in the bulk review form for a person to check and apply. Suggestions are hints; nothing changes until someone applies a review. Schema version 13.
- Groups of similar untriaged findings: a new **Groups** page puts the latest trend run's untriaged findings into groups at least 85% alike (80 to 95% to choose), each led by its most important finding, largest first, with its rules, severities, components and suggestions. **Review these together** opens the Findings page filtered to the group, for one bulk review. Groups are worked out from the stored vectors and the current reviews; the dashboard never calls Ollama.
- The Overview's **Similar findings** panel shows how much of the latest trend run has embeddings, how many need a new one (missing, or the message changed), when they were made, and how many untriaged findings have a suggestion, with the `triage embed` command to run when some are missing.
- Sign-in through an OpenID Connect provider, such as Dex, in place of the shared login token. The first start runs a setup wizard, which needs a one-time code printed on the server's console, tests the provider (discovery, RS256 signing keys, PKCE, scopes and the client credentials) and saves the settings in `oidc.toml` (mode 0600). A private CA's certificate is pasted in the wizard and kept as `oidc-ca.pem`; the wizard never takes a file path. Sign-in uses the authorization code flow with PKCE, state and nonce, and checks the ID token's RS256 signature, issuer, audience, expiry and nonce, in plain Python. Admins are those whose ID token carries the admin claim (by default the `shoal-admin` group); anyone else needs an admin to allow their verified email address, on a new **Users** page or with `shoalscan serve user allow|disallow|disable|enable|list`. `shoalscan serve oidc show|reset` shows or resets the settings. Reviews and configuration changes are recorded under the person's email address. **`shoalscan serve token` and the shared token are removed:** after upgrading, start `shoalscan serve` and run the setup wizard.
- The dashboard's Configuration page chooses each registered repository's scanners: **As the policy says**, or **Choose here** with one box per scanner, showing its pinned version and whether it is installed on the server. The choice is written into the managed policy as a `scanners` line under a marker, validated and audited like every other change.
- A finding missing from a scheduled run verifies a "fixed" review only if the run used the finding's scanner, so turning a scanner off never marks its findings as fixed.
- `tools.lock` can pin a scanner in its own table, with the download, the binary in it and its extra files. A lock without such a table stays valid.

### Fixed

- `shoalscan scan` no longer warns about Opengrep's signature when Opengrep is not among the scanners.
- A `.shoalscan.toml`, baseline or dashboard policy nested deeply enough to exhaust Python's stack (thousands of `[` or `{`) is now reported as not valid TOML, instead of stopping with a `RecursionError` traceback. Found by the new fuzz targets.
- The dashboard's setup wizard counts a setup code that is not plain ASCII as a wrong code, instead of dropping the request.
- The dashboard accepts an OpenID Connect issuer with a trailing slash, and compares it exactly as the provider publishes it.
- Suggestions are worked out for the latest trend run (the newest scheduled run, as on the dashboard), not for the newest run of any kind, so a pull-request run no longer decides which findings get one.
- Suggestions and groups stay quick on large histories: suggestions compare at most the 1,000 most recently decided findings with at most 5,000 untriaged ones; `triage embed` reads only each finding's newest text from the database; similarity is a dot product of the stored unit vectors (in C on Python 3.12 and later); and the dashboard keeps each run's groups until its embeddings or the reviews change, so the Groups page and a group's findings no longer compare every vector on each request.
- A malformed scanner report (a severity or level that is not text, a list of lines or references that is not a list, a location of the wrong shape) is now a scan error that names the problem, instead of a traceback. A `findings.json` that is not UTF-8, is nested too deeply, or has a field of the wrong type is refused as unreadable or malformed. Found by the new fuzz targets.
- `findings.json` records Trivy's verification as it really happened: `"sha256 and cosign"` only when `shoalscan install` checked its signature (it now writes `trivy.verified.json` after the check), and `"sha256 (signature not verified)"`, with a warning from `scan`, after `install --skip-signature-check`. Running `install` again with cosign verifies a binary that was installed without the check.
- Scanner output is read as it is written, with a cap on each stream; a scanner that writes more than its cap is stopped and the scan fails, instead of everything being held in memory first.
- `install` matches a release archive's member by its exact name (only a leading `./` is ignored), so a differently named member can never stand in for the scanner.
- The dashboard's run page lists the scanners each run used, with their versions.
- Files Trivy logs as failing to parse (a Dockerfile it cannot read, say), not only Terraform files, are listed as not fully scanned.

### Security

- `findings.sarif` no longer copies the scanned code: the `snippet` of every Opengrep result (its region, context region, related locations and code flows) is removed. A snippet held the whole matched line, so a rule that finds hard-coded secrets put the secret itself into a file that CI uploads or keeps as an artifact. Locations, messages and fingerprints are unchanged.
- Nothing in a scanned repository can silence Gitleaks: its `.gitleaks.toml`, `.gitleaksignore` and `gitleaks:allow` comments are ignored, and the configuration environment variables are not passed. False positives go into the baseline.
- Nothing in a scanned repository can silence Hadolint: its `.hadolint.yaml` (and one in the home directory) and `# hadolint ignore=` pragmas are ignored, and `HADOLINT_*` variables are not passed.
- Nothing in a scanned repository can silence zizmor or send it online: it runs with `--offline`, `--no-config` and `--no-ignores`, without tokens or `ZIZMOR_*` variables, and a `.gitignore` cannot hide a workflow from it.
- Nothing in a scanned repository or on the machine can silence Trivy: its `trivy.yaml`, `.trivyignore`, cached checks and home-directory modules are not read, and `TRIVY_*` variables are not passed. Its inline ignore comments, which cannot be turned off, must name one check and an issue or they block, and they are counted with the other suppressions.
- The secrets Gitleaks finds never reach the findings, the SARIF file, `check.json` or the history: the report stays in the scan's private temporary directory, and fingerprints hash the matched line with the secret masked.
- Text from the scanned repository (paths, messages, rule metadata, baseline reasons, component names, review descriptions) is escaped in the work list and the report, so it cannot add links, images, HTML or headings.
- Dashboard admin sessions last at most one hour, after which the admin signs in again and the provider's admin claim is read again, so removing someone from the admin group takes effect within the hour. Disabling someone still takes effect at once. Member sessions keep their limits.
- The dashboard keeps no server-side state for a sign-in in progress: the state, nonce and PKCE verifier travel in the `__Host-` login cookie, signed with HMAC-SHA256 under a key held only in memory, and each state works once; when too many used states are still current, new sign-ins are refused for a few minutes rather than one being forgotten. Starting sign-ins can no longer push out other people's. Starting a sign-in is rate limited per client address with a token bucket (a burst of 30, then one every 10 seconds), so clients behind one shared address can still sign in together.
- One person holds at most 10 dashboard sessions; signing in again ends their own oldest session, never someone else's.
- The one-time setup code is written to `setup-code` in the state directory (mode 0600) instead of the console output, and it expires after 30 minutes; the file is deleted once it expires.
- The dashboard accepts only ASCII email addresses, checks the ID token's `azp` whenever it is present, and briefly remembers that the provider could not be reached, so sign-ins do not queue behind a network timeout.
- Suggestions for similar findings take decisions only from dashboard reviews and from the baseline of scheduled runs of the target's configured branch (recorded with `--kind scheduled`, an operator action that is trusted). A reason in a pull request's own baseline is part of the change under review, and no longer suggests a status for findings like it. Each suggestion now says where its decision comes from: a review, by whom and when, or the baseline of a scheduled run, with the run, the commit and the day.
- **Use the suggestion** sets only the status of the bulk review. The similar finding's reason is shown read-only, for reference, and is never copied into the description: the reviewer writes their own, so each review and each baseline entry `triage export` makes from it is in the words of the person who checked it.
- C1 control characters (U+0080 to U+009F) and bidirectional formatting characters (U+061C, U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069) are now treated like other control characters: folded away in the work list, the report and the terminal output of `check`, `triage suggest-similar` and `history list-runs`, replaced with U+FFFD in stored text and review descriptions (where they no longer count toward the 10-character minimum), and escaped in baseline files. A policy diff printed by `check` shows them, and other control characters, as U+FFFD.
- Gitleaks report paths with `..` in them are refused as outside the target.
- The Ollama client refuses redirects instead of following them, and the largest answer it reads is about 26 MiB (a batch of the longest vectors, with room to spare) instead of 256 MB.
- Gitleaks now never reads a repository's `.gitleaksignore`, in every mode: when one exists, Gitleaks scans a private staging copy of the tree without it, and the file itself is scanned for secrets on its own (deeper `.gitleaksignore` files are scanned like any other file). Previously the top-level file could still drop findings despite `--gitleaks-ignore-path`.
- Gitleaks lists the files it skips for their size as not fully scanned, so they count, and fail a pull request's check when changed, like other unscanned files.
- Trivy's inline ignore comments are linted in every spelling Trivy 0.74.0 accepts, including the legacy `tfsec:` prefix, keys before `ignore` (such as an expiry date), white space other than a space inside the comment, wildcards anywhere in the id, files over the size limit and packaged charts. Each must name one check and an issue. A finding Trivy reports as silenced without a valid comment at or above it now fails the scan.
- Scanners are isolated from the machine: each run gets an empty private home and temporary directory, git with no configuration and no allowed transport, proxies on a closed local port, the cloud metadata services turned off, and, where available, an operating-system network sandbox (`sandbox-exec` on macOS, `unshare --net` on Linux), with a warning when there is none. Remote Terraform modules can no longer be fetched during a scan, and the user's SSH keys, git credentials and cloud credentials are out of reach. `findings.json` records the isolation used.
- Scans started from the dashboard or at night always pass their policy explicitly: the managed policy, or else the `.shoalscan.toml` at the head of the registered branch, so the commit being scanned (an older commit, on a rescan) never chooses its own scanners.
- Gitleaks runs with its pinned rules minus every allowlist that matches on path names (`node_modules/`, `vendor/`, lock files, `*.pdf`, paths containing `gitleaks.toml` and others) or on the text around a secret (the whole match or the line, such as a variable's name), so a repository cannot place a secret where Gitleaks does not report it. Only stopwords and patterns on the secret's value are kept. Leave paths out with `excludes`, which is policy.
- Every letter-case variant of `.gitleaksignore` at the top of the tree is treated as the ignore file, as a case-insensitive file system makes Gitleaks read it, and the staging copy is checked to hold none before Gitleaks runs. A cross-device staging copy is limited to 4 GiB.
- Helm charts are rendered by Shoalscan with a pinned Helm 4.2.4 (SHA-256 pinned, its PGP signature checked when pinned), offline, isolated and within time and memory limits, and checked unchanged as Kubernetes manifests; Trivy's own Helm scanner, which reads ignore comments a template can write at render time, is off. A chart whose output holds anything like an inline ignore marker is not checked and blocks instead. Findings are reported at the template named by Helm's own header (or at `Chart.yaml`), never dropped. A chart that does not render, lacks its dependencies, holds a link or renders too slowly or too large is listed as not fully scanned. Extra values files are named under `[trivy.helm_values]`. The About page lists Helm.
- `shoalscan scan --require-network-sandbox` fails unless the scanners can run in an operating-system network sandbox. The dashboard's worker requires it by default (`require_network_sandbox = false` in `scan_targets.toml` turns it off), and so does `examples/scheduled-scan.sh` (`SHOALSCAN_REQUIRE_NETWORK_SANDBOX=0`). Without a sandbox, a scanner can still reach services on this machine's loopback interface; the documentation now says so.
- The scan worker keeps each scan's temporary files in its own work directory, which is removed even when the scan is stopped at the deadline, and removes work directories an earlier, killed worker left behind.
- Scanner error messages (a Dockerfile that does not parse, a workflow zizmor cannot read, any scanner failure) no longer quote the scanned files: code frames and quoted text are removed, keeping the kind of error and the file path.

### Project

- The code follows PEP 8 with 120-character lines, formatted and checked by Ruff 0.14.0 (a development tool, pinned by hash in `requirements-dev.txt`, never a dependency). CI runs `ruff check` and `ruff format --check`. `CloneTooLarge` in the scan worker is now `CloneTooLargeError`.
- Ruff also checks for likely bugs (its `B` rules, from flake8-bugbear): every `zip()` now says whether its inputs must be the same length, and they must everywhere in Shoalscan, so a mismatch is an error instead of silently dropped data.
- A command and file reference, `docs/reference.md`: every command, the exit codes, and the files Shoalscan reads and writes. `SECURITY.md` names every scanner's upstream and describes the OpenID Connect sign-in.
- Fuzz targets for the scanner reports Shoalscan reads (Gitleaks, Trivy, Hadolint and zizmor) and for `findings.json`, each checking that every finding is well formed and in a file of the repository. The `fuzz` workflow and `docs/development.md` list every target.
- Fuzzing: `fuzz/targets.py` holds fuzz targets for the parsers that read untrusted input (`.shoalscan.toml`, the baseline, suppression markers, the Markdown escaper, and ID tokens, both arbitrary and correctly signed with arbitrary claims), each checking a contract rather than only "no crash". The `fuzz` workflow runs each under Atheris (pinned by hash in `requirements-fuzz.txt`, never a dependency) for a minute on pull requests that change the code and ten minutes weekly; the unit tests run every target over its seeds and random edits of them.
- CodeQL leaves out the deliberately insecure test fixtures in `rules/` and `tests/data/`, as Shoalscan's own scan does; the alerts raised on them were dismissed as false positives.

## 0.1.0 (2026-10-11)

The first release: Opengrep install, scan, baseline and check, plus the run history and the dashboard.

### Run history and dashboard

### Added

- `shoalscan record` stores a run in a SQLite history database: the findings, the check summary (counts by severity, the blocking and non-blocking split, new and stale findings, the baseline size, suppressions and files not fully scanned), and the repository, ref, commit, time and kind (`pr` or `scheduled`). The database has a schema version and migrations, uses WAL mode, and is created with mode 0600. Recording is idempotent per repository, commit and kind. Findings are stored by their identity, so the dashboard can tell when each was first seen and when it was fixed. Runs are capped in size and old runs are pruned.
- `shoalscan serve` starts a dashboard over HTTPS for one or more repositories. The Overview page shows open findings by severity over time, the baseline burn-down, new and fixed findings per week, the mean time to fix, the age of open findings, findings by component, suppressions and files not fully scanned over time, and the latest run's result. The Findings page has a filterable table that links each rule to its message; the Runs page lists the history; the About page explains the name, lists the pinned scanners and rule sources with their licences, and states the limits of static analysis. The Shoalscan icon is the logo and the favicon. The pages are plain HTML, CSS and JavaScript with inline SVG charts, in a light and a dark theme.
- `shoalscan serve token` makes a 256-bit login token and stores only its SHA-256.
- `shoalscan serve init-tls` uses the `openssl` command to make a single-use certificate authority, name-constrained to the dashboard's addresses and host names, which signs one server certificate and then has its key deleted. You can also bring your own certificate and key.
- `examples/scheduled-scan.sh` scans the head of the default branch in a temporary worktree each night and records it, with example launchd and systemd timer units.
- `parse_warn_only` in `.shoalscan.toml`: globs of changed files whose partial parses only warn, for languages whose Opengrep parser is experimental (Dockerfiles, shell scripts, YAML templates). Skipped files, timeouts and other errors still fail. Under `--policy-ref` the list comes from the base branch. Each such file is listed loudly and counted in the summary.
- `parse_warn_only` also covers whole-file syntax errors of template files (Helm templates, Jinja YAML): they warn as SYNTAX ERROR (warn-only by policy) instead of failing; skips, timeouts and other errors still fail.
- `shoalscan check` writes `check.json` next to the findings: the new and new blocking findings, the stale baseline entries and what happened to each changed file. The findings file lists the inline suppressions.
- `shoalscan record` stores the check's outcome and exit status (`--check-exit`) and the lists from `check.json`, findings, suppressions and unscanned files, in schema version 3. Older runs stay readable. A run whose check could not run is recorded as a scan error, without results; it feeds no trend and never replaces a run with results.
- `shoalscan history list-runs` and `shoalscan history delete-run --yes` to find and remove a run, for example one recorded with a temporary configuration.
- The dashboard says what each run's result means: Passed, Blocked with its reasons, or Scan error, with a link to the new blocking findings. Every number with a list behind it is a link: the tiles, the severity chart's points and legend, the weekly and age bars, and the cells of a new component heatmap ranked by heat score. New pages list a run's stale baseline entries, unscanned files and suppressions, and the findings behind each week's new and fixed counts. Filters live in the address, so views can be bookmarked and shared.
- `examples/scheduled-scan.sh` takes `SHOALSCAN_PYTHON` and refuses a Python older than 3.11; it passes the check's exit status to `record`.
- The Overview's **Blocking findings** panel: the findings the policy treats as blocking, split into new (fail pull requests) and baselined (the backlog), a line of the count over the scheduled runs, and the ten to fix first. The Findings page has a Blocking only filter and a Fix priority sort: new blocking first, ERROR before WARNING, the hottest component, then the oldest. `check.json` lists the blocking class and `record` stores it (schema version 4); older runs show it as unknown.
- `shoalscan history delete-run` records each deletion (schema version 5), and the Runs page says how many runs were deleted.
- Finding reviews (schema version 10): mark findings as false positive, accepted risk, won't fix or fixed, one by one or in bulk, always with a description; scheduled runs verify fixes and flag regressions; every change is kept with its time and author. Baselined findings show their baseline reason until reviewed. The Overview counts untriaged blocking findings and regressions. `shoalscan triage export` prints reviewed findings as baseline entries for a reviewed change; reviews alone never change what blocks CI.
- Scanning from the dashboard, off until repositories are registered in `scan_targets.toml`: **Run a fresh scan** on the Runs page, **Rescan** of a repository's tip or of exactly one run's commit, and a **Configuration** page that edits the registered repositories under strict rules. Scans run in a detached worker (`shoalscan scanjob`) with a lock, a deadline, cooldowns and an hourly cap, and are audited (schema versions 6 and 7), as are configuration changes (schema version 8). `shoalscan scanjob --nightly` scans every nightly repository, with example launchd and systemd units.

### Security

- `parse_warn_only` entries must name files: a file name, a name with any extension, or an extension, optionally under a path. Catch-alls such as `*e*` or `**` are refused, and an entry without `/` never matches a directory. The setting binds a pull request only under `--policy-ref`.
- `record` binds a run to the commit that was scanned, which `scan` now writes into `findings.json`; findings from a `--no-git` scan need `--allow-no-git`. It also refuses a `check.json` whose lists do not agree with the summary's counts.
- Control characters in rule ids and component names are replaced when a run is recorded, and a bad recorded value shows as plain text instead of breaking a dashboard page.
- The dashboard serves TLS only. Login is a rate-limited form POST compared in constant time; sessions use a `__Host-` cookie that is `Secure`, `HttpOnly` and `SameSite=Strict`; every POST must be same-origin and logout needs a CSRF token. Responses carry a strict same-origin Content Security Policy with no inline code and no framing, `nosniff`, a referrer policy and HSTS. Unknown `Host` headers are refused. Static files come from a fixed list. The database is opened read-only with parameterised queries, and untrusted text is only ever inserted as text.

### Install, scan, baseline and check

### Added

- `tools.lock` pins Opengrep 1.30.2 for Linux and macOS on x86_64 and arm64, cosign 3.1.3, and the final commit of the archived opengrep-rules repository, each by URL and SHA-256.
- `shoalscan install` downloads the pinned tools over HTTPS, checks every SHA-256, checks the Opengrep signature with `cosign verify-blob` against the Opengrep release workflow identity, and moves files into place atomically. It installs only the rule languages Shoalscan uses and keeps the rules' licence file next to them. Running it again verifies what is installed. Without cosign it stops, unless `--skip-signature-check` is given.
- `shoalscan scan` runs Opengrep offline with local rules only and writes `findings.json` and `findings.sarif`. Any scanner failure fails the scan. Fingerprints survive line shifts.
- `shoalscan check` compares the findings with the baseline. New blocking findings and stale baseline entries fail; INFO findings never block. It prints a report and a one-line `SHOALSCAN_SUMMARY` JSON summary, and exits 0, 1 or 2.
- `shoalscan baseline init` writes a sorted, deterministic baseline from a full scan and refuses to overwrite one without `--force`.
- The suppression lint: an inline suppression must name a rule id and an issue, or it becomes a blocking finding. Suppressions are counted.
- `.shoalscan.toml` configuration with strict validation.
- Rule selection: `[opengrep] categories` (default `["security"]`) picks community rules by their category, and `[opengrep] exclude_rules` leaves out rules by id or `prefix.*`. The selected rules are copied to a temporary directory; the installed snapshot is never changed.
- `non_blocking_paths`: findings under these path prefixes are reported but never fail the check.
- Shoalscan's own Opengrep rules, with tests: TLS verification turned off, plain `http://` URLs, secrets passed to log calls, and broad exception handlers that swallow security-check failures.
- CI examples for GitHub Actions and for a self-hosted runner.
- `--policy-ref` for `scan` and `check`: on pull requests the configuration, the baseline and the repository's rule directories come from the base branch. The baseline may only shrink, policy edits are shown as a diff, and `blocking` must include ERROR.
- Files Opengrep skipped or reported errors for are listed; a changed file that was not fully scanned fails a pull request.
- `shoalscan baseline rename-path OLD NEW` for moved files.
- `examples/CODEOWNERS`.

### Hardening

- The installed community rules are checked against a digest pinned in `tools.lock`, not against a manifest in the tools directory.
- The tools and output directories must be outside the repository; their defaults are now the user's cache directory and a private temporary directory.
- The suppression lint uses Opengrep's own grammar, reports bare suppressions as bare, and covers every scanned file, prose included.
- Fingerprints include the enclosing function or class and no longer include the path.
- Rule selection refuses YAML it cannot read with certainty, checks that the split text reassembles exactly, and checks the rules Opengrep ran against the staged ones.
- Opengrep runs with an allowlisted environment; downloads respect their deadline on every read; unexpected errors exit with 2.
- A cosign mismatch is reported as possible tampering; an install without a signature check is recorded and verified on the next install.
- Rules: more secret-in-log forms; `http://localhost@host` is reported; constants are reported once.
- The GitHub Actions example's SARIF upload now runs, and the self-hosted script reinstalls on a new pin.
- `--policy-ref` accepts only a full commit SHA or a fully qualified `refs/heads/...` or `refs/remotes/...` ref, so a tag cannot shadow the base branch; the workflow passes the base commit SHA.
- The suppression lint uses ASCII word boundaries, as Opengrep does.
- Fingerprint contexts are qualified (`class:A/def:run`), and line numbers follow newlines only.
- The rule reader refuses duplicate or continued category values and unclosed quotes; a PyYAML-generated list of the pinned snapshot's categories is checked in and tested.
- `check` refuses findings for a different tree; scans record the HEAD tree and a dirty flag.
- A signature counts as verified only with a positive record of the cosign check.
- Unscanned changed files are graded (partial parses near added lines or covering most of a file fail); pure baseline moves are allowed under strict conditions; first-time adoption is supported.
- Rules: more secret-in-log forms (Python `extra` keys and `getLogger(...)`, Node object fields, Rust `%field` and `println!`).
- The suppression lint folds the long s as Opengrep does; changed files under excludes are listed; `check` needs a git work tree unless `--no-git`; quoted rule ids and categories may not contain backslashes; secret-in-log covers keyword arguments and `creds`.

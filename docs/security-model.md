# Security model

This guide collects how Shoalscan protects itself: the scan, the dashboard and the worker that scans from the dashboard. [Limits](limits.md) lists what these safeguards do not cover.

## Scans and the policy

- Scanner binaries and the community rules are pinned by SHA-256 in `tools.lock`, and the Opengrep and Trivy cosign signatures are checked at install time ([Getting started](getting-started.md#install-the-pinned-scanners)).
- A scan makes no network calls, and the scanners are kept off the network and away from this machine's credentials ([details](#scanner-isolation)).
- Nothing in the scanned repository can configure a scanner or silence it: Opengrep ignores `.semgrepignore` files, Gitleaks never reads a `.gitleaksignore` at all and ignores `.gitleaks.toml` and `gitleaks:allow` comments, Hadolint ignores `.hadolint.yaml` and `# hadolint ignore=` pragmas, zizmor runs offline and ignores `zizmor.yml` and `# zizmor: ignore` comments, and Trivy runs offline with its embedded checks and ignores `trivy.yaml`, `.trivyignore` and modules in the home directory; its inline ignore comments, with either the current or the legacy prefix, must name one check and an issue, and a finding Trivy silenced without such a comment fails the scan ([Scanners](scanners.md)). Inline suppressions for Opengrep must name a rule and an issue.
- Files a scanner skips for their size are listed as not fully scanned, so they count, and fail a pull request's check when they changed, like any other file that was not scanned.
- The scan records what was really verified: a scanner installed with `--skip-signature-check` is recorded, and reported, as "signature not verified".
- Scanner errors are kept without the scanned code: lines of a code frame and quoted text are removed from them before they reach an error message, a log or the history, leaving what went wrong and the file.
- Secrets that Gitleaks finds never reach the findings, the SARIF file or the history ([details](scanners.md#the-secrets-stay-out-of-the-output)).
- The tools directory and the output directory must be outside the repository, so a pull request cannot plant files in them.
- A scan that fails in any way fails the command; it is never read as "no findings".
- On a pull request with `--policy-ref`, the configuration, the baseline and the rule directories come from the base branch, so a change cannot relax its own checks ([details](baseline-and-check.md#pull-requests-the-policy-comes-from-the-base-branch)).
- [Test scope](test-scope.md) accepts a finding automatically only for the Opengrep rules the policy lists (read from the base branch under `--policy-ref`), only in Rust files, and only when the finding's whole byte range lies inside an item that Opengrep's own parser proves is compiled for tests alone (`#[cfg(test)]`); whole files and test functions never count, and every match's spelling is checked again. The base branch and the CI environment are trusted. A pull request keeps test scope only when every path it changes is Rust source (not a special Cargo or rustup name in any spelling, not under `target/` or `node_modules/`, not deleted, linked or re-moded), and a merge base git cannot find turns it off. The whole tree is also checked: any build script, or a Cargo or toolchain file outside its allowlist (compilers, linkers, wrappers other than allowed ones, `[patch]` from outside the repository, `rustflags` beyond `-C`, `-L`, `-l` and lint levels), turns test scope off, with names compared after Unicode normalisation and case folding. Building without `--cfg test` in the CI environment is the operator's responsibility. Secret rules and Gitleaks rules are refused: a secret in test code is still a leak. Accepted findings stay in every output, and their automatic reviews are recorded as "shoalscan (test scope)".
- Scanning and recording need no token or secret. The dashboard holds one, the client secret for your identity provider, in a 0600 file in its state directory.
- Similar-finding suggestions use an embedding model on this machine only: finding text (never code) goes to Ollama on the loopback interface, without proxies, at a host set on the command line and never by the scanned repository ([details](triage.md#similar-findings-with-a-local-embedding-model)).

## Scanner isolation

A repository can ask a scanner to fetch things. Trivy, for one, downloads the remote Terraform modules a repository names (`git::`, `s3::`, `gcs::`, https and the Terraform registry), and version 0.74.0 has no flag to stop it: `--tf-exclude-downloaded-modules` only filters results. So every scanner run is kept apart from the machine:

- **An empty home of its own.** `HOME` and the temporary directory are a new directory, mode 0700, removed when the run ends. The real home directory's SSH keys, git credential helpers, `~/.aws`, `~/.config/gcloud` and tool configuration are out of reach.
- **An allowlisted environment.** Only `PATH`, the locale, the user name and the time zone pass through. Cloud credentials (`AWS_*`, `GOOGLE_*`, `AZURE_*`), tokens, `SSH_AUTH_SOCK` and every scanner's own configuration variables do not.
- **Git that goes nowhere.** `GIT_CONFIG_NOSYSTEM=1` and `GIT_CONFIG_GLOBAL=/dev/null` (no credential helpers or URL rewrites), `GIT_ALLOW_PROTOCOL` empty (no transport at all, `file://` included), `GIT_TERMINAL_PROMPT=0`, and an SSH command that always fails.
- **Proxies that go nowhere.** `HTTP_PROXY`, `HTTPS_PROXY` and `ALL_PROXY` (in both cases) point at a closed port on the loopback interface, with `NO_PROXY` empty, and the AWS and Google metadata services are turned off. This stops connections to other hosts, but not to this machine: Go programs never send a request for `localhost` or `127.0.0.1` through a proxy, so without a sandbox a scanner can still reach services on the loopback interface. Only the sandbox below cuts that off.
- **A network sandbox, where the operating system has one.** On macOS each scanner runs under `sandbox-exec` with a profile that denies IP networking and DNS. On Linux it runs in a new network namespace (`unshare --net`, with an unprivileged user namespace), which has no interface but a loopback that is down. Shoalscan tries each once per process; when none works (Linux without unprivileged user namespaces, or inside another sandbox), it prints a warning and relies on the environment alone. `findings.json` records which was used under `isolation`.
- **Requiring the sandbox.** `shoalscan scan --require-network-sandbox` fails, before any scanner runs, when no sandbox works. The dashboard's worker passes it by default (`require_network_sandbox` in `scan_targets.toml`), and so does `examples/scheduled-scan.sh` (`SHOALSCAN_REQUIRE_NETWORK_SANDBOX=0` turns it off). A plain `shoalscan scan` does not require it, even when Trivy runs: CI runners often lack unprivileged user namespaces, they are short-lived and seldom run other services, and requiring it there would mostly push people to turn Trivy off. Pass the flag wherever a scan runs on a long-lived machine.

For the strongest isolation, which we recommend for scans of untrusted code, also run Shoalscan where the network is cut off by the platform: a container started with `--network none`, or a CI job or virtual machine without network access. Scanning needs no network once `shoalscan install` has run.

## The dashboard

- It speaks TLS 1.2 or later only, with forward-secret AEAD ciphers. There is no plain-HTTP port.
- People sign in through an OpenID Connect provider: the authorization code flow with PKCE (S256), a `state` bound to a short-lived cookie, and a `nonce`. The ID token comes straight from the provider's token endpoint over TLS, authenticated with the client secret, and its RS256 signature is checked against the provider's keys (2048 bits or more; every other algorithm is refused), with its issuer (exactly as the provider publishes it), audience, authorised party (`azp`, whenever the token has one), expiry and nonce.
- The server keeps no state for a sign-in in progress, so starting many sign-ins cannot push out anyone else's. The state, nonce and PKCE verifier travel in the `__Host-` login cookie (`Secure`, `HttpOnly`, ten minutes), with an HMAC-SHA256 tag under a key that exists only in the dashboard's memory. The cookie is signed rather than encrypted, because the standard library has no authenticated encryption: nobody can make or change a cookie the dashboard accepts, and the PKCE verifier in it is readable only by someone who can already read the browser's cookie, who could finish that sign-in with the cookie anyway. The state that comes back must be the one in the cookie, and each state works once: the dashboard remembers used states until their sign-in would have expired, the callback clears the cookie, and the provider refuses a code used twice. The dashboard remembers at most 10,000 used states; when that many have not yet expired, it refuses new sign-ins for a few minutes rather than forget one.
- Starting a sign-in is rate limited per client address with a token bucket: a burst of 30, then one every 10 seconds. Addresses do not affect each other, and a busy address recovers on its own. The dashboard sees the address of whatever connects to it: behind a reverse proxy, a load balancer that terminates connections, NAT or a container's port mapping, every client shares one address, and so shares this limit, the failed sign-in limit and the connection limits. The burst is sized so that a team can still sign in together through one address.
- When the provider cannot be reached, the dashboard remembers that for 30 seconds and refuses sign-ins at once in that time, rather than letting each wait for the network. The provider must use https with a checked certificate (plain http only on the loopback interface), and proxy settings are ignored.
- Until sign-in is set up, the dashboard serves only the setup wizard, which needs a one-time setup code, so whoever reaches the port first cannot set it up. The code is written to `setup-code` in the state directory (mode 0600), never to the console output, which often ends up in journals and container logs; the console names the file. The code works for 30 minutes, and a restart makes a new one. Wrong codes, including ones that are not plain text, are rate limited.
- Admins are those whose ID token carries the admin claim, checked at every sign-in. An admin session lasts at most one hour, after which the admin signs in again and the claim is read again, so taking someone out of the admin group at the provider takes effect within the hour. Anyone else needs an admin to allow their verified email address, which must be plain ASCII (so that no two addresses fold to the same one). A person's first sign-in binds their address to their account at the provider. Roles are checked on the server for every request, and every session against the people list, so disabling someone or taking back their access ends their sessions at once. The client secret and the people list are kept in 0600 files in the state directory, apart from the history.
- Failed sign-in callbacks are rate limited per address, as wrong setup codes are.
- A session is a `__Host-` cookie that is `Secure`, `HttpOnly` and `SameSite=Strict`. Sessions live only in memory, end after eight idle hours, after seven days (one hour for an admin), and at once when their person is disabled or loses access. One person holds at most 10 sessions: signing in again ends their own oldest one, never someone else's. The dashboard holds at most 100 sessions in all; when it is full, the least recently used session ends.
- Every POST must come from the dashboard's own origin, and logout also needs the session's CSRF token.
- Every response carries a strict Content Security Policy (only the dashboard's own scripts, styles and images, no inline code, no framing), `nosniff`, a same-origin referrer policy and HSTS.
- Requests with an unknown `Host` header are refused, which defeats DNS rebinding.
- Static files come from a fixed list, so a request path can never reach another file.
- Requests and connections are bounded. A request URL may be 4,096 bytes and a body 2,048 bytes; a chunked body is refused and the connection closed. The server holds at most 64 connections, 16 from one address, and only 4 from one address that have not finished the TLS handshake. A handshake must finish within 5 seconds, and a connection lives at most 60 seconds. Errors the HTTP parser raises carry the same security headers as every other response.
- The database is opened read-only, and every query is parameterised. The one write is at start: an older database is migrated, after a backup copy, as `record` does. Finding messages and paths are shown as text, never as HTML.

### The certificate

`shoalscan serve init-tls` makes a single-use certificate authority that signs one server certificate and then has its private key deleted. Its name constraints limit it to the dashboard's own DNS names and IP addresses, and it may vouch only for TLS servers, so trusting it does not let anyone impersonate other sites in a client that enforces name constraints. [The dashboard](dashboard.md#serving-the-dashboard) has the details and how to trust it.

## The scan worker

Scanning from the dashboard is off until repositories are registered in `scan_targets.toml`, which must be owned by the user that runs Shoalscan and not writable by anyone else ([Scanning from the dashboard](dashboard-scanning.md)).

A request to scan names a registered repository and nothing else. The worker always gives the scan its policy explicitly: the managed policy (or the configuration file set in `scan_targets.toml`) when there is one, else the `.shoalscan.toml` at the head of the registered branch, read from git. So the commit being scanned never chooses its own scanners, not even an older commit scanned again with **Rescan this commit** ([details](dashboard-scanning.md#which-policy-a-scan-uses)). Each run records which scanners ran, with their versions, and the run's page shows them. No path, branch, ref, flag or command text ever comes from the browser. Starting a scan is a POST that needs a session, the CSRF token and the dashboard's exact `Origin` header. One scan runs at a time, with a per-repository cooldown and an hourly cap for all repositories.

The web server never scans. It starts one detached worker, `python -m shoalscan.scanjob`, with a fixed argument list, no shell, a new session, an allowlisted environment and its output in a log in the state directory. The worker reads `scan_targets.toml` again and takes only the repository's name from the server. It takes a lock file that names its process; a lock whose process has gone, or whose process number now belongs to another process, is stale and is taken over. It fetches the clone, scans the head of the branch in a temporary worktree, and runs `scan`, `check` and `record --kind scheduled --check-exit` with a deadline. At the deadline the whole process group is killed and nothing is recorded. Temporary files are removed on every exit path. The log lines the Runs page shows have every absolute path removed.

- **Git attributes.** The worker reads git attributes from an empty tree (`GIT_ATTR_SOURCE`), so a scanned repository's `.gitattributes` cannot make a checkout run a filter driver. This needs git 2.40 or later, and Shoalscan checks before every scan that git really honours it ([details](dashboard-scanning.md#requirement-git-240-or-later)).
- **Clones.** A public `source` is cloned over https only, from an allowed host, with no prompts and no credential helpers. Clones and fetches are size-limited, and a scan needs a minimum of free disk space. Private repositories are scanned from mirrors you keep up to date yourself, so Shoalscan never needs their credentials.
- **Rescan this commit** sends only the repository's name and a run number; the worker looks the commit up in the history database and checks that it is a full commit SHA still in the clone.
- **The Configuration page** can set only a few checked fields (name, source, branch, enabled, nightly and the policy text), and refuses, never cleans up, a value that does not fit. It can never set a path, an interpreter, a timeout or command text. Every change is written atomically at mode 0600 and audited. Baselines change only from the command line ([details](dashboard-scanning.md#the-configuration-page)).
- **Audit.** Every scan and every configuration change is recorded in the history database with who, when and the outcome.
